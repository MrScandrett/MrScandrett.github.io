What Is Pathfinding?

What Is Pathfinding?

Pathfinding is the problem of finding a route between two points through a space that has obstacles, costs, or rules attached to it. That space might be a grid on a screen, a road network, a warehouse floor, or the inside of a computer chip — the algorithm doesn't care what the "space" represents, only how it's connected.

In Software

Every time a map app reroutes you around traffic, a game character walks toward you around a wall, or a delivery app schedules stops on a route, pathfinding is running underneath. It's also inside tools you wouldn't expect: network routers use pathfinding-style algorithms to decide how a data packet hops from server to server, and chip designers use it to route the microscopic wires connecting a processor's components without letting any two cross.

In Hardware

A warehouse robot planning a route between shelves, a robot vacuum mapping a room, a drone weaving between obstacles, and a factory arm avoiding a collision are all solving a pathfinding problem — but now a wrong answer costs real time, real hardware, or a real collision instead of a wasted frame. Hardware pathfinding also usually has to run continuously as the world changes, not just once at the start.

Biomimicry: Borrowing From Nature

Some of the best pathfinding ideas were discovered by biologists, not computer scientists. Ants leave pheromone trails that evaporate over time, so shorter round-trips get reinforced faster than long ones — a decentralized way for a whole colony to converge on an efficient path, now used in ant colony optimization for shipping and network routing. Slime mold, given oat flakes arranged like a map's cities, grows a network of tubes that closely mirrors real-world rail systems, because it prunes inefficient connections as it grows. Flocking birds and schooling fish navigate collision-free as a group using only simple local rules, which is the same idea behind "boid" simulations that give game crowds and swarms of robots believable, coordinated movement without any one member planning the whole route.

The Evolution of Pathfinding: Games and Real Life

The Evolution of Pathfinding: Games and Real Life

Pathfinding has gotten steadily smarter as hardware got faster and the problems it needed to solve got harder.

Video Games: From Grids to Navmeshes

Pac-Man's ghosts (1980) used simple, almost hard-coded chase rules on a small maze grid — there wasn't enough processing power for much else. By the 1990s and 2000s, real-time strategy games like StarCraft and Age of Empires needed dozens of units pathfinding across large maps simultaneously without freezing the game, which pushed developers toward more efficient search and shared, precomputed route data. Modern 3D games mostly don't search a grid at all — they search a navigation mesh, a set of connected walkable polygons draped over the 3D level, which is far faster to search than checking every tiny tile.

Real Life: From Paper Maps to Live Rerouting

Early car navigation and mainframe route planning (1960s–1980s) could only compute a static shortest path on a fixed map, computed once, well ahead of time. Consumer GPS navigation in the 1990s–2000s brought this to a dashboard, but still assumed the road network didn't change mid-trip. Today's map apps continuously re-run pathfinding using live traffic data, treating slow roads as temporarily higher-cost edges — the same g(n)/h(n) idea in this lab, just rerun every few seconds on a vastly bigger graph.

The Future of AI Pathfinding

The Future of AI Pathfinding

Classic algorithms like A* guarantee a correct answer, but they still search a known map with a hand-designed heuristic. The active research now is about what happens when the map is huge, unknown, shared by many agents, or changing faster than a search can keep up with.

Learned Heuristics

Instead of a programmer designing h(n) by hand — Manhattan distance, Euclidean distance, or zero — machine learning models can be trained on millions of past searches to predict a much better estimate of remaining cost, letting A*-style search check far fewer nodes on huge, complex maps like real city road networks.

Reinforcement Learning

Rather than searching a graph at all, an agent can learn a movement policy directly by trial and error in a simulated environment — useful when the "cost" of a path is hard to define in advance, like a robot arm avoiding a fragile object or a legged robot crossing rubble.

Multi-Agent Coordination

Warehouses like Amazon's run hundreds of robots on the same floor at once, where the hard problem isn't finding any one robot's path — it's finding paths for all of them that don't collide or deadlock each other, which needs its own family of algorithms on top of A*.

The core idea from this lab — balance what you already know against your best guess of what's ahead — keeps showing up at every layer of this progress, from a single rover on a grid to a fleet of self-driving cars.

Why Pathfinding?

Why Pathfinding?

Pathfinding shows up any time something needs to move — or spread — intelligently through a space. It's one of the most common sources of real complexity in a student game project, and it's rarely just one question.

Five Different Questions

"Pathfinding" is really a family of related problems, and picking the right one saves a lot of wasted effort:

  • ConnectivityAre these two locations connected at all?
  • ReachabilityWhat are all the locations connected to this one?
  • Any pathFind some path between two locations — it doesn't need to be good.
  • Fewest stepsFind the path between two locations with the fewest steps.
  • Lowest costFind the path between two locations with the lowest total cost, when steps aren't all equal.

Case Study: Pac-Man

Ghosts chasing Pac-Man, creepers in Minecraft, or units routing between cities in a strategy game all need one or more pathfinding algorithms just to move believably. This is usually baked into the "minimum viable product" for any game with intelligent enemies — it isn't an optional extra.

Case Study: Floodfill

Not every use of pathfinding looks like a maze. In a bubble-shooter game, popping a bubble destroys every same-colored bubble connected to it — and separately checks whether any bubbles are still connected to the ceiling. Both checks are pathfinding in disguise. The same idea is the paint-bucket tool in an image editor: "fill everything connected to this pixel" is a reachability search, usually called floodfill.

Graphs: The Map Behind the Maze

Graphs: The Map Behind the Maze

Every pathfinding algorithm searches a graph — a set of nodes (locations) connected by edges (connections between them). How you build that graph from your actual problem determines which algorithm fits.

Directed vs. Undirected

An edge is undirected when it works both ways — like a hallway you can walk down in either direction. It's directed when it only works one way, like a one-way street.

Weighted vs. Unweighted

A graph is unweighted when every edge costs the same to cross. It's weighted when some edges cost more than others — a longer street, a slower terrain, a pricier flight.

Same Idea, Different Graphs

  • Train routes between citiesUndirected + weighted — trains run both ways, but routes differ in length.
  • Pac-Man's mazeUndirected + unweighted — any two open cells without a wall between them cost the same one step.
  • Bubble-shooter connectionsUndirected + unweighted — same-colored neighboring bubbles are simply connected or not.
  • City streetsDirected + weighted — one-way streets exist, and block lengths vary.

The Algorithm Family: DFS → BFS → Dijkstra → A*

The Algorithm Family: DFS → BFS → Dijkstra → A*

A* didn't appear from nowhere — it's the last step in a short chain of increasingly smart search strategies. Each one solves the previous one's biggest limitation.

Depth First Search (DFS)

Picks a direction and commits, backtracking only when it hits a dead end — the same idea as recursive backtracking. Great for solving a maze, finding any path, or floodfill. Doesn't care whether the path it finds is short.

Breadth First Search (BFS)

Visits the start node's neighbors, then their neighbors, then theirs — radiating outward one full ring at a time. Whichever ring reaches the goal first has, by construction, the fewest steps. Guarantees the shortest path only when every edge costs the same — an unweighted graph.

Dijkstra's Algorithm

BFS's fix for weighted graphs. Instead of expanding ring by ring, it always expands whichever unvisited node currently has the cheapest known distance from the start — and it will happily revise a node's best-known cost if a cheaper route to it turns up later. Guarantees the lowest-cost path with nonnegative movement costs, but explores in every direction equally, with no sense of where the goal actually is.

A* Algorithm

A small but powerful upgrade to Dijkstra: it adds a heuristic — an estimate of remaining distance to the goal — so it expands nodes that seem to be heading the right way first. With a consistent estimate, as on this rover grid, it finds the lowest-cost path and can check fewer cells than Dijkstra. That's exactly f(n) = g(n) + h(n) in the How A* chooses above: cost-so-far plus estimated-distance-remaining.

Building Up: Try Them in Order

If you're implementing any of this yourself, don't start with A*. Build Dijkstra first — it only needs loops and a couple of data structures to track distances and parents — and confirm it finds correct lowest-cost paths. Then add a heuristic to turn it into A*. Trying to write A* from scratch first means debugging two ideas — shortest-path search and heuristic guidance — at once.

A* (A-Star) Algorithm A* finds the shortest path by combining g(n) — actual cost from start — with h(n) — a heuristic estimate to the goal. It always expands the node with the lowest f(n) = g(n) + h(n).
Manhattan Heuristic Counts horizontal + vertical steps to the goal. Best for grid movement with no diagonals. Typically expands fewer nodes than Euclidean on axis-aligned grids.
Euclidean Heuristic Straight-line distance to the goal. On this four-direction rover grid, it never exceeds the true remaining cost, but usually gives a lower estimate than Manhattan.
Zero Heuristic (Dijkstra) Setting h(n) = 0 turns A* into Dijkstra's algorithm: guaranteed optimal but explores many more nodes since it has no directional guidance.
Fuel Critical Mode Adds a maximum cost budget. If no path exists within the fuel limit, the mission fails — showing how real-world constraints change planning.
Step Mode Advance one node expansion at a time. Watch how the open set (frontier) and closed set (visited) grow — this is the core of how A* "thinks."

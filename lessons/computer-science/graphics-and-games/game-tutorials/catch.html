🗺️ The Architecture

Every tiny-loop game starts as a concept, then gets broken into a core loop, a systems list, and a structure — before anyone touches sprites or colors. Here's the Catch Game's architecture:

🌱ConceptMove to catch the good things falling from the sky, avoid the bad ones.
→
🔁Core LoopMove → item falls → touch it → score or life changes → repeat.
→
🧩SystemsPlayer movement, item spawner, collision check, score/lives tracker.
→
🏁Win/LoseReach the score goal to win, run out of lives to lose.

The four systems, in order of execution every frame:

  1. Input system — reads which arrow key is held and moves the player rectangle left/right.
  2. Spawner system — every ~1 second, drops a new item (good or bad) at a random x position at the top.
  3. Physics system — every falling item's y position increases each frame (gravity).
  4. Collision system — checks every item against the player's box (AABB); good touch → +1 score, bad touch → −1 life, and missing a good item resets your catch streak.

🏛️ The Origin: Catch-and-Dodge Arcade Loops (1980–Present)

Moving horizontally along the bottom edge to intercept falling objects is one of video gaming's oldest and clearest verbs. Players understand the rules in two seconds without reading a single word of instructions.

1980 · Nintendo

Gunpei Yokoi's Game & Watch: Ball

On a tiny LCD calculator screen with fixed black segments, players shifted two hands left and right to juggle falling balls—proving pure timing and spatial anticipation needed zero scrolling worlds.

1981 · Atari 2600

Larry Kaplan's Kaboom!

An analog paddle dial let players sweep buckets at lightning speed to catch falling bombs while accelerating spawn rates pushed reaction time to its limit.

Today · Arcade Fairness

Risk vs. Reward Spawning

Mixing collectible stars with hazardous bombs forces split-second decisions: should you dash across the screen for a star, or hold position to dodge a bomb right above it?

📐 The Physics of Hitboxes: AABB Collision & Arcade Fairness

In 2D games, rectangular sprites are tested for overlap using Axis-Aligned Bounding Boxes (AABB)—four fast inequalities checking X and Y ranges. Professional arcade games shrink hazard hitboxes to ~70% of the visible sprite so grazing corners feels fair instead of frustrating.

🟡 Naive Sprite-Edge Collision

  • Tests the full emoji/sprite bounding rectangle including transparent corners.
  • Near-misses trigger unfair hits when corners barely graze empty space.
  • Randomly spawning items without spacing checks can drop overlapping hazards.

🔵 Arcade-Tuned Catch Engine

  • Shrinks hazard hitboxes (~70%) so players feel clever dodging by a hair. The game above does this: a bad item's box is 20 px inside its 28 px sprite, while good items keep the full 28 px so catches feel generous.
  • Tracks a reachability cone: fall time × player speed limits how fast items may drop.
  • Turn on 🔍 X-Ray in the game HUD above to see live AABB boxes while you play!

👀 Peek at the Code

The game running above is this code — nothing hidden. It's split into two parts on purpose: a small config object you just edited with the panel, and a locked engine that reads it.

✏️ Config — this is what the panel above edits 
const config = {
  player: '🤖',
  good:   '⭐',
  bad:    '💣',
  bg:     'space',
  speed:  3,
  winScore: 10,
  startLives: 3
};

👆 This block updates live. Change anything in the panel and the matching value flashes here. There's no separate "demo" version of the code; this is it.

🔒 Engine — locked, shared by every version of this game 
function update() {
  // 1. move the player from held keys
  if (keys.left)  player.x -= 5;
  if (keys.right) player.x += 5;

  // 2. spawn a new item on a timer
  if (timeSinceSpawn() > spawnRate) spawnItem();

  // 3. move every falling item down
  items.forEach(i => i.y += config.speed);

  // 4. check collisions, update score/lives
  items.forEach(i => {
    if (collides(player, i)) {
      i.type === 'good' ? score++ : lives--;
      i.remove = true;
    }
  });
}
This is what "architecture" means in practice: the config is the part of the design doc you filled out in Lesson 1 (goal, mechanic, feedback). The engine is the part no one writes twice — it's the same four systems for every Catch Game anyone ever builds, yours included.

Why the Limits?

Real game engines work exactly this way: a locked core (physics, rendering, input) and an open layer of content (sprites, levels, tuning) built on top. You're practicing that split before you ever write the locked part yourself.

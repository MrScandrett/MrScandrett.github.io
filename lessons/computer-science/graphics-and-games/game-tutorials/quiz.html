Content settings change how it looks and apply instantly. Rule settings change how it plays, so the round restarts.

Notice what you can't change here: there's no field for "how answer-checking works" or "how the progress bar advances." That's the engine — the part every version of this game shares. You're only tuning content (and writing questions), not rewriting architecture. That's the limit, on purpose.

What these actually touch in the engine: Retries per Question only sets the starting value of retriesLeft each time a question renders — the same retriesLeft <= 0 check in onChoice() decides when to reveal the answer and advance, whatever that starting number is. Question Set swaps in a whole different questions array — onChoice() never looks at whether a question is math, science, or animals, only at choices and correct.

🗺️ The Architecture

Every tiny-loop game starts as a concept, then gets broken into a core loop, a systems list, and a structure — before anyone touches sprites or colors. Here's the Quiz Adventure's architecture. Notice this one is different from the others: almost all of the design work is writing, not programming — the engine is short.

🌱ConceptAnswer questions correctly to advance through the quest.
→
🔁Core LoopQuestion shown → pick an answer → correct advances, wrong gives a hint → repeat.
→
🧩SystemsQuestion display, answer check, hint/retry, progress tracker.
→
🏁Win/LoseAnswer the final question to finish the quest. There's no lose state.

The four systems, in order of execution on every answer:

  1. Question display system — shows the current question's text and its answer choices as buttons.
  2. Answer-check system — compares the clicked choice against the question's correct answer.
  3. Hint/retry system — a wrong answer shows a hint and uses up one retry; running out of retries reveals the answer so no one gets stuck. The buttons lock while the game moves on, so a fast double-click can't skip a question.
  4. Progress system — a correct (or revealed) answer advances the progress bar to the next question, or ends the quest on the last one.

🏛️ The Origin: Data-Driven Trivia & Quiz Engines (1985–2013)

Quiz games proved a powerful engineering idea early on: if you separate the question database from the quiz engine, teachers, writers, and players can swap entire subjects without changing a single line of code.

1985 · Broderbund

Where in the World Is Carmen Sandiego?

Stored hundreds of geography clues in structured tables so a compact game engine could assemble fresh detective chases on early Apple II computers.

1995 · Jellyvision

You Don't Know Jack

Turned trivia into a snappy TV-show state machine: prompt → lock input → witty feedback → score reveal, proving UI pacing matters as much as questions.

2013 · Classroom Tech

Kahoot! & Quiz Platforms

Scaled the exact content/engine split to millions of classrooms: one locked quiz state machine powered by infinite user-written question arrays.

📐 Deep Dive: Fisher-Yates Shuffling & State Machine Guards

🟡 Hardcoded Questions & Naive Sort

  • Writing a separate if/else function per question explodes code size.
  • choices.sort(() => Math.random() - 0.5) is biased in JavaScript engines.
  • Missing a locked state lets rapid clicks skip two questions at once.

🔵 Data-Driven Arrays + State Guard

  • Any questions array of { text, choices, correct, hint } runs automatically.
  • Fisher-Yates swaps backward from n - 1 to 1, giving every order equal 1/n! odds.
  • Watch the live STATE badge in the HUD above step through ASKING → LOCKED!

👀 Peek at the Code

The game running above is this code — nothing hidden. It's split into two parts on purpose: a small config & question-set object you just edited with the panel, and a locked engine that reads it.

✏️ Config & Content — this is what the panel above edits 
const config = { theme: 'math', avatar: '🧙', retries: 3 };

const questions = [
  { text: '5 + 7 = ?', choices: ['10', '12', '13'], correct: 1, hint: 'Count up from 7, five times.' },
  // ...more questions
];

👆 This block updates live. Change anything in the panel and the matching value flashes here. There's no separate "demo" version of the code; this is it.

🔒 Engine — locked, shared by every version of this game 
function onChoice(choiceIndex) {
  const q = questions[currentIndex];

  if (locked) return;       // ignore clicks while we're moving on

  // 1. check the answer
  if (choiceIndex === q.correct) {
    locked = true;
    advance();  // 2. correct: move to the next question, or win
    return;
  }

  // 3. wrong: show the hint, use up a retry
  retriesLeft--;
  showHint(q.hint);
  if (retriesLeft <= 0) { locked = true; advance(); }  // 4. out of retries: reveal & advance
}
This is what "architecture" means in practice: the config here is bigger than usual — it includes the actual questions, because in a Quiz Adventure the writing is the content. The engine is still the part no one writes twice: the same display, check, hint, and progress systems run every quiz you ever build, whatever the subject.

TwistA countdownNew system: time pressure

Give each question 10 seconds. When time runs out, it counts as a wrong answer. Now the game rewards fluency as well as knowledge. Is that what you want for a learning game? Different subjects might answer that differently.

timeLeft--;                          // once a second

Why the Limits?

Real game engines work exactly this way: a locked core (physics, rendering, input) and an open layer of content (sprites, levels, tuning) built on top. You're practicing that split before you ever write the locked part yourself.

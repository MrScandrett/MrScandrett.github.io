🎮 Play & Customize

Move with ← / →, A / D, or your mouse/finger. Fire with Space, ↑, a click/tap on the game, or the touch Fire button. Targets drift, so lead your shots. The clock is running: hit the score goal as fast as you can.

Score: 0 0.0 s

Keys only work while the game has focus. Press P or Esc to pause.

Tune the Game (limited, on purpose)

Content settings change how it looks and apply instantly. Rule settings change how it plays, so the round restarts.

Notice what you can't change here: there's no field for "how targets respawn" or "how hits are detected." That's the engine — the part every version of this game shares. You're only tuning content, not rewriting architecture. That's the limit, on purpose.

What Projectile Speed actually touches in the engine: it's only how many pixels each projectile's y shrinks by per frame once it's already in flight (p.y -= config.projectileSpeed) — it doesn't touch how often you can fire (there's no cooldown; one key press is one projectile) or how close a projectile has to be to register a hit in collides(). Same fire rate and hit radius at every speed.

🗺️ The Architecture

Every tiny-loop game starts as a concept, then gets broken into a core loop, a systems list, and a structure — before anyone touches sprites or colors. Here's the Top-Down "Shooter"'s architecture:

🌱ConceptAim and fire at targets before time or patience runs out.
→
🔁Core LoopMove → fire a projectile → it travels → hits a target → target disappears, score +1.
→
🧩SystemsPlayer movement, projectile spawner, target spawner, hit detection.
→
🏁Win/LoseReach the score goal to win. There's no lose state — just accuracy and speed.

The four systems, in order of execution every frame:

  1. Input system — reads held arrow keys to move the player along the bottom, and a key press to fire.
  2. Projectile system — each fire press spawns one projectile at the player's position that travels straight up until it hits something or leaves the screen.
  3. Target spawner system — keeps three targets drifting side to side near the top, respawning a new one in a random slot a moment after one gets hit.
  4. Hit detection system — checks every projectile against every target with AABB; on a hit, the target disappears, the projectile is removed, and the score increases.

🏛️ The Origin: Fixed Shooters & Projectile Loops (1962–1981)

Spawning short-lived projectiles from a player sprite and testing them against moving targets created one of the most influential loops in gaming history—and taught engineers how to manage dynamic object lists efficiently.

1962 · MIT

Steve Russell's Spacewar!

Running on a PDP-1 minicomputer, two spaceships fired vector torpedoes across a CRT—pioneering projectile physics and real-time hit checks.

1978 · Taito

Tomohiro Nishikado's Space Invaders

Locked the player to a horizontal track along the bottom and introduced wave-based target rows, shields, and escalating tempo as targets were cleared.

1981 · Namco

Galaga & Target Variety

Added swooping dive paths, double-shot power-ups, and end-of-stage accuracy bonuses—rewarding smart aim over blind button mashing.

📐 Deep Dive: Predictive Lead Geometry & Hit Pools

Because projectiles take time to travel upward (t = Δy / v_shot), firing directly at a moving target aims at where it was. Smart players—and turret AI—aim ahead by Δx = v_target × t so shot and target arrive at the same spot together.

🟡 Unfiltered Arrays & Double Hits

  • Never deleting off-screen projectiles leaks memory and slows collision loops down.
  • Without a p.hit guard, one shot overlapping two targets could score twice!
  • Instant teleporting lasers remove all skill of reading target speed.

🔵 Filtered Pools + p.hit Guard

  • projectiles.filter(p => p.y > -10 && !p.hit) sweeps dead shots every tick.
  • Checking !p.hit && t.alive ensures each shot scores at most once.
  • Turn on 🔍 X-Ray in the HUD above to see the 44×44 hitboxes and drift vectors!

👀 Peek at the Code

The game running above is this code — nothing hidden. It's split into two parts on purpose: a small config object you just edited with the panel, and a locked engine that reads it.

✏️ Config — this is what the panel above edits 
const config = {
  theme:  'balloons',
  player: '🧑',
  projectileSpeed: 4,
  winScore: 15
};

👆 This block updates live. Change anything in the panel and the matching value flashes here. There's no separate "demo" version of the code; this is it.

🔒 Engine — locked, shared by every version of this game 
function update() {
  // 1. move the player from held keys
  if (keys.left)  player.x -= 5;
  if (keys.right) player.x += 5;

  // 2. fire spawns one projectile that travels straight up
  if (firePressed) { projectiles.push({ x: player.x, y: player.y }); firePressed = false; }
  projectiles.forEach(p => p.y -= config.projectileSpeed);

  // 3. targets drift and bounce; empty slots refill after a short delay
  targets.forEach(t => {
    t.x += t.vx;  if (t.x < 24 || t.x > W - 24) t.vx *= -1;
    if (!t.alive && --t.cooldown <= 0) respawn(t);
  });

  // 4. check every projectile against every target
  projectiles.forEach(p => targets.forEach(t => {
    if (t.alive && collides(p, t)) { t.alive = false; p.hit = true; score++; }
  }));
}
This is what "architecture" means in practice: the config is the part of the design doc you filled out in Lesson 1 (goal, mechanic, feedback). The engine is the part no one writes twice — the same movement, projectile, spawner, and hit-detection systems power every top-down target game, whatever the theme.

Give the player 20 shots. When they're gone, the game ends and the score is your accuracy (hits / shots). It's the same engine, but now the design rewards patience instead of speed.

if (firePressed && shots < 20) fire();
if (shots === 20 && projectiles.length === 0) endGame(score / shots);

Why the Limits?

Real game engines work exactly this way: a locked core (physics, rendering, input) and an open layer of content (sprites, levels, tuning) built on top. You're practicing that split before you ever write the locked part yourself.

Keep It Nonviolent

Every theme here targets objects, not characters — balloons, trash, viruses, fires. That's a deliberate design choice for a classroom target game, not a limitation of the mechanic.

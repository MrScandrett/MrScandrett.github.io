Lesson 09 · Servers · 50–65 minutes

Run your site on a real server

Double-clicking index.html opens a file. It does not visit a website. In this lesson you turn your own computer into a web server, learn to read the address it gives you, watch it answer requests, and use that server to load your site's content from a data file with fetch().

Everything here stays on your computer. Nobody else can see your site until you publish it in the next lesson. That makes this the safe place to test.

This page came from a server.

Before you start

  • A project folder with index.html, style.css and script.js at the top, from your first site or a starter pack.
  • A terminal: the one built into VS Code (Ctrl+`) is fine.
  • One of these: the Live Server extension, Node.js, or Python. Ask your teacher which one your computer is allowed to use.

No install allowed at all (a locked school laptop or a Chromebook)? Read along and do both labs on this page. They run on the class site's own server. Web Studio previews your files without a server.

Double-clicking is not a server

When you double-click a file, the browser's address bar starts with file://. There is no server: the browser reads the file straight off your disk. Simple pages look fine that way, so it is easy to think nothing is missing. Then you add one modern feature and it fails with a red error you did not cause.

A web server is a program that waits for a browser to ask for a file, finds it, and sends it back with a short label saying what it is. When that program runs on your own computer, the address starts with http://localhost. That is how every real website is delivered, so it is the honest way to test.

The fetch() failure is the one you will meet first. In Chrome the console says something like this:

Access to fetch at 'file:///…/my-site/projects.json' from origin 'null'
has been blocked by CORS policy: Cross origin requests are only
supported for protocol schemes: http, data, https …

Read it calmly. Origin 'null' means "this page came from no server". The fix is not in your code. Start a server and open the page through it.

Read a localhost address

Every server prints an address when it starts. It has the same four parts as any web address, and each part is worth knowing:

http://localhost:8080/pages/about.html

The four parts of a local address
PartHereWhat it means
SchemehttpHow to talk to the server. Locally, plain http is fine because the request never leaves your computer.
HostlocalhostWhich computer. localhost is a name that always means this computer. 127.0.0.1 is the same thing written as a number.
Port8080Which program on that computer. One computer runs many programs that talk to the network, so each one listens on its own numbered port. Only one program can hold a port at a time. Live Server usually picks 5500, npx serve 3000, Python whatever you tell it.
Path/pages/about.htmlWhich file, counted from the folder the server was started in. That folder becomes /.

The last row is the one that causes trouble. If you start the server in the folder above your site, every address needs an extra folder name in it, and your /style.css links break. Always start the server inside the folder that holds index.html.

Start a server: pick one way

All three do the same job. Use whichever your computer already has. First, in the terminal, move into your site folder and check that index.html is there:

cd my-site
ls

On Windows Command Prompt, use dir instead of ls. If you don't see index.html in the list, you're in the wrong folder. Fix that before going on.

Watch the server answer

A server that you start in a terminal prints one line for every request it answers. Load your page once, then look. Python's log looks like this:

127.0.0.1 - - [19/Nov/2026 10:42:01] "GET / HTTP/1.1" 200 -
127.0.0.1 - - [19/Nov/2026 10:42:01] "GET /style.css HTTP/1.1" 200 -
127.0.0.1 - - [19/Nov/2026 10:42:01] "GET /script.js HTTP/1.1" 200 -
127.0.0.1 - - [19/Nov/2026 10:42:01] "GET /images/Logo.png HTTP/1.1" 404 -

One page is several requests: the HTML first, then every file it links to. Each line says who asked (127.0.0.1 or ::1, both mean you), what they asked for (GET /style.css) and the status code the server answered with. The browser's Network panel (F12 → Network) shows the same list from the browser's side.

Status codes you will see from a static server
CodeMeaningWhat to do
200 OKFound it; here it is.Nothing.
304 Not ModifiedThe browser already had this file and it hasn't changed, so the server sends nothing new.Nothing. If your change doesn't show up, do a hard reload (Ctrl/Cmd+Shift+R).

    Load your content with fetch()

    So far your project cards have been typed into index.html. Many real sites keep the content in a separate data file instead, and JavaScript builds the cards from it. Add a project by adding three lines to the data file, and every page that uses it updates. That only works through a server, which is why it's here.

    projects.json

    [
  {
    "title": "Orbit study",
    "kind": "Simulation",
    "description": "A moon circles a planet."
  },
  {
    "title": "Star catcher",
    "kind": "Game",
    "description": "Catch falling stars."
  }
]

    JSON is strict: double quotes only, and no comma after the last item. One stray comma and the whole file fails to read.

    script.js

    async function showProjects() {
  const list = document.querySelector('#projects');
  try {
    const response = await fetch('projects.json');
    if (!response.ok) {
      throw new Error(`${response.status} for projects.json`);
    }
    const projects = await response.json();
    for (const project of projects) {
      const card = document.createElement('article');
      const title = document.createElement('h3');
      title.textContent = project.title;
      const text = document.createElement('p');
      text.textContent = project.description;
      card.append(title, text);
      list.append(card);
    }
  } catch (error) {
    list.textContent = 'Projects could not load: ' + error.message;
  }
}
showProjects();

    In your HTML, give it somewhere to go: <section id="projects"></section>.

    • fetch() asks the server for a file, the same way the browser asked for style.css. The answer takes time, so await waits for it without freezing the page. await only works inside an async function.
    • A 404 is still an answer. fetch() doesn't fail when the file is missing. It returns a response with ok set to false. Always check response.ok.
    • response.json() turns the text into real JavaScript arrays and objects.
    • textContent, not innerHTML, puts the words on the page. If the data ever contains < or a script, it shows as text instead of running.
    • The catch puts the problem on the page. A visitor should see "Projects could not load", not a mysteriously empty section.

    Data from other sites

    You can fetch() from another website too (weather, space photos, museum collections), but two rules apply.

    • The other site decides. A browser only lets your page read another site's answer if that site's server says so in its reply. That permission is called CORS. If an API doesn't allow it, nothing in your code can change that. Pick an API whose documentation says it works from the browser.
    • No keys in your JavaScript. Many APIs hand out a secret key. Anything in script.js can be read by every visitor, so a key there is a key you've given away. For a class site, choose APIs that need no key at all.

    Test on a phone

    npx serve prints a second address, labelled Network:, such as http://192.168.1.24:3000. That is your computer's address on the Wi-Fi. A phone on the same network can open it and show your real site on a real small screen.

    • Many school networks block one device from reaching another, so it may simply not load. That's the network doing its job. Use the browser's device toolbar (F12, then the phone icon) instead.
    • While the server runs, anyone on that network who finds the address can read every file in the folder you served. Python and serve listen to the whole network by default. Serve only your site folder (never your home folder or Documents) and stop the server when you finish.

    What this kind of server can't do

    Every server in this lesson, and GitHub Pages, is a static server. It hands out files exactly as they are on disk. It runs none of your code itself: your JavaScript runs in the visitor's browser.

    A static server can

    • Serve pages, styles, scripts, images, sound and video
    • Serve data files your JavaScript reads with fetch()
    • Run games, simulations and tools in the visitor's browser
    • Remember things for one visitor in their own browser (localStorage)

    It needs a back end to

    • Save a message from a contact form
    • Keep a high-score table that every player shares
    • Let people log in
    • Keep a secret key secret

    A back end is a program you write that runs on the server, usually with a database, in a language like JavaScript (Node.js) or Python. It's the next step after this course, and it brings real responsibility for other people's data. For now, be honest on your page about what a form does, as the HTML lesson asks.

Set Up Your First Site

By the end of this lesson you will have a folder on your own computer holding three files that work together, and you will be able to explain what the browser asked for and what it got back.

Nothing here is throwaway practice. The folder you build now is the folder you keep for the rest of the course. Give it a good name and put it somewhere you can find again.

Build this website with blocks

Try another way to build: snap together HTML, CSS and behavior blocks, change their fields, and watch your website update. Start with this lesson’s project or try a code example below.

Step 1 — Install and open Visual Studio Code

Visual Studio Code (VS Code) is a free text editor. It does not build your site and it does not run it — it writes plain text files, and the browser does the rest. This course uses it because its file tree makes folder structure visible, and folder structure is most of what goes wrong for beginners.

  1. Download VS Code from code.visualstudio.com and install it. On a school device, ask whether it is already installed or needs an administrator.
  2. Open VS Code. Close the welcome tab. You want an empty editor with a sidebar.
  3. Make a folder for your site first, in your file manager, before you touch the editor. Call it my-site. Use a lowercase name with no spaces — you will be typing it later, and spaces in web addresses turn into %20.

You do not need a single extension to finish today. If you want the ones this course assumes later, see the VS Code setup lesson.

Step 2 — Open a folder, not a file

This is the step people skip, and it costs them an hour later. In VS Code choose File → Open Folder… and pick my-site. Do not use Open File.

A website is never one file. It is a folder of files that refer to each other by name. With the folder open, the sidebar shows every file in it, new files land inside it, and the paths you type match what is really on disk. Open a single file instead and you are editing something with no visible neighbours — which is how you end up with a stylesheet the browser cannot find.

Check: the sidebar's top row says MY-SITE. If it says OPEN EDITORS with one lonely file and no folder name, you opened a file. Close it and open the folder.

Step 3 — Create the three files

With the folder open, use the "New File" button at the top of the sidebar three times and create exactly these names:

  • index.html — the content and structure. This is the only file the browser asks for by itself.
  • style.css — the design: colour, spacing, size, layout.
  • script.js — the behaviour: things that happen after the page is on screen.

The part after the dot is the file extension, and it is not decoration. It tells the browser how to interpret the bytes inside. A stylesheet saved as style.txt is a text file that happens to contain CSS, and the browser will refuse to apply it. VS Code gives you a clue: an .html file gets colour highlighting and tag completion. If your file looks grey and plain, check the extension.

Windows and macOS often hide extensions in the file manager, and they usually treat Index.HTML and index.html as the same file. Most web servers — including GitHub Pages, where this course publishes — do not. Filename case matters. A link to Style.css that works perfectly on your laptop can return a 404 the moment the site is online, and that is a genuinely miserable bug to chase. Type every filename in lowercase, every time, and type the link the same way.

Step 4 — The smallest real index.html

Type this into index.html. Type it rather than pasting it: the shape of a document is worth having in your fingers.

<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>My site</title>
  <link rel="stylesheet" href="style.css">
  <script src="script.js" defer></script>
</head>
<body>
  <h1>My site</h1>
  <p>This page is running from my own computer.</p>
</body>
</html>

Every line is doing a job:

What each line of the skeleton is for
LineJob
<!doctype html>Switches the browser into modern standards mode. Leave it out and it falls back to old, inconsistent behaviour.
<html lang="en">Declares the page's language, so screen readers pick the right pronunciation.
<head>Information about the page. Nothing in here is drawn on screen.
<meta charset="utf-8">Says the text is UTF-8, so accents and every other alphabet survive. Without it you get characters like â€™.
<meta name="viewport"…>Tells phones to use the real device width instead of shrinking a desktop layout.
<title>The tab name, the bookmark name, and the first thing a search result shows.
<body>Everything a visitor actually sees.

Step 5 — Connect the other two files

Your three files do not know about each other until the HTML says so. Two lines do all the connecting:

<link rel="stylesheet" href="style.css">
<script src="script.js" defer></script>

<link> has no closing tag and no visible content. The rel="stylesheet" part is the browser's instruction for what to do with the file it fetches; without it the file is downloaded and ignored. href is the address.

<script> always needs a closing </script>, even when it is empty. The defer attribute means "download this now, but do not run it until the HTML is finished." That matters because JavaScript usually wants to find elements on the page, and it cannot find what the browser has not read yet. Leave defer off, put the script in the head, and your code will look for an <h1> that does not exist yet and quietly get null.

Now put something obvious in each file so you can prove the connection worked.

/* style.css */
body {
  background: #10233c;
  color: #f4f7fb;
  font-family: system-ui, sans-serif;
  padding: 2rem;
}
// script.js
console.log("script.js is running");

Pick a background colour you would never choose on purpose. This first style is evidence, not taste: a subtle change proves nothing, because you cannot tell it from the default.

Step 6 — Open the page, and see it fail on purpose

There are two ways to open your page.

  1. Double-click index.html in your file manager. The address bar shows something starting with file:/// — the browser is reading files straight off your disk.
  2. Run a local server — the Live Server extension in VS Code, or a one-line command such as python3 -m http.server run inside your folder. The address bar shows http://localhost:5500 or http://localhost:8000.

For today, double-clicking is fine and everything in this lesson will work. Later it will not be. Under file:/// there is no server, so anything that needs a request to one is unavailable: fetch() of a local JSON file is blocked, and so are JavaScript modules (type="module"). Those are security rules, not bugs, and no amount of correct code gets around them. Switch to a local server the moment your site loads data — it is also the only honest rehearsal for publishing, because a real host is a server.

Repair: the browser opened your HTML as text, showing the tags instead of the page? The file is saved with the wrong extension — probably index.html.txt. Rename it and turn on "show file extensions" in your file manager.

Step 7 — Prove the CSS and the JavaScript really loaded

"It looks fine" is not evidence. Check both connections on purpose.

  1. CSS: the page background is the ugly colour you chose. If it is still white, the stylesheet did not arrive.
  2. JavaScript: open the developer tools (F12, or Ctrl+Shift+I, or Cmd+Option+I on a Mac) and click the Console tab. You should see script.js is running. If the console is empty, the script did not arrive.
  3. Both: click the Network tab and reload. You should see three rows — index.html, style.css, script.js. A red row or a 404 is the browser telling you it asked for a file at that exact address and there was nothing there.

That screen is the whole model of the web. The browser asked for one document, read it, found two references inside, and made two more requests. It never scanned your folder and it never guessed — it fetched exactly the names you wrote. Almost every "why isn't my CSS working" question is answered by those rows.

When a file is missing, the fault is almost always one of four things: the filename is spelled differently from the link, the case is different, the extension is wrong, or the file is in a different folder than the path says. That last one is what the lab below is for.

Lab — Trace the route

A path in href or src is directions, not a location. A relative path starts from the folder holding the HTML file you are writing in. ../ means "go up one folder to the parent"; a name with no slash and no dots means "a file sitting right here beside me."

Here is the folder your site is growing into. Trace each answer with your finger before you type it.

my-site/
├── index.html
├── style.css
├── script.js
├── images/
│   └── logo.svg
└── pages/
    └── about.html

Write the path

Pick a question, type the path exactly as you would type it in the HTML, and check it. Answers are lowercase, with forward slashes.

Trace from the current HTML file’s folder. Then check your route.

Check: a correct answer names the destination and nothing more. From index.html, the stylesheet is simply style.css — you are already in the right folder, so there is nothing to travel. Reaching into a folder adds the folder name and a slash: images/logo.svg.

Repair: from pages/about.html you are one folder deep, so every route out starts with ../ to climb back to my-site/. From there you carry on as if you were index.html: ../index.html, or ../images/logo.svg. A leading slash, /images/logo.svg, means something else — "start at the very top of the site" — and it breaks under file:///. Avoid it for now.

Finish and save your evidence

Before you close the editor, screenshot your page beside the console showing script.js is running, and save it in your project folder. That is your proof the three files were connected, and you will want it when something breaks later and you need to know what "working" looked like.
